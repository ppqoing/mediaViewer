# 分片 MP4 播放进度兼容设计

- 日期：2026-08-03
- 状态：已确认
- 适用范围：Android 应用内通过 HTTP/HTTPS 播放的 MP4 视频
- 用户确认边界：仅修改应用端，不改变服务器配置，不转码或重封装源文件

## 1. 目标

修复部分 fragmented MP4（fMP4/DASH MP4）在实际只播放数秒时，播放器下方时间和进度条已跳到视频末尾附近的问题。

修复必须只对可靠识别出的 fMP4 启用 LibVLC `avformat` 解复用器。普通 MP4、音频及其他媒体格式继续使用当前播放路径，MediaSession、播放队列、进度持久化、后台播放和 UI 状态链路均保持不变。

## 2. 已确认根因

对用户提供样本及同目录对照文件的实际检查得到以下证据：

- 目标视频的容器、视频流和音频流时长均约为 `111.483` 秒，媒体文件本身没有错误的总时长。
- 文件具有 `dash` 兼容品牌、`mvex`、`sidx` 和连续 `moof` 等 fMP4 结构，编码器标记为 GPAC。
- LibVLC 播放日志出现 `Fragment sequence discontinuity detected`。
- 目标视频实际播放约四秒时，LibVLC 原始 `TimeChanged` 已依次跳到约 33、58、79、93 和 108 秒；因此应用 UI 收到的原始位置本身就是错误的。
- 同目录另一份 GPAC fMP4 也会快速跳到末尾，而普通平坦 MP4 在播放七秒后正确显示约七秒。
- HTTP 服务支持字节范围请求，并返回正确的媒体长度和 `video/mp4` 类型。

因此，本问题发生在 LibVLC 原生 MP4 解复用器处理此类分片时间线时，不属于此前已经修复的 Media3 客户端位置外推问题。继续过滤 UI 时间、使用墙钟补偿或修改位置快照链路只能掩盖症状，不能恢复正确的解复用、seek 和播放时钟。

## 3. 方案选择

采用“播放前小范围探测 + 仅对 fMP4 使用 `avformat`”方案：

1. 对 HTTP/HTTPS 的 `.mp4` 地址读取文件开头最多 64 KiB。
2. 使用边界安全的 ISO Base Media File Format Box 解析器识别 fMP4 特征。
3. 只有识别为 fMP4 时，向 LibVLC Media 添加 `:demux=avformat`。
4. 未识别、探测失败或非 MP4 媒体继续使用当前默认解复用路径。

未采用以下方案：

- 不对所有 MP4 强制使用 `avformat`，避免扩大到已经正常播放的 MP4，并降低硬件解码、字幕、seek 或特殊封装产生回归的风险。
- 不在 UI 层过滤“看起来跳得太快”的时间，因为正常 seek、倍速和特殊时间线也可能产生大幅跳变，且过滤无法修复底层播放时钟。
- 不引入 ExoPlayer 与 LibVLC 双引擎路由，因为本缺陷只需更换 LibVLC 内部解复用器，双引擎会显著扩大队列、后台播放、音轨和状态同步范围。
- 不要求服务器或媒体库预先重封装，遵守已确认的应用端兼容边界。

## 4. 组件与职责

### 4.1 播放源描述

新增内部播放源值对象，包含：

- 已由现有端点逻辑生成的完整请求 URL；
- 解复用策略：`DEFAULT` 或 `AVFORMAT`。

URL 必须原样沿用现有请求地址，不重新拼接路径，避免中文、空格、百分号编码和查询参数被二次编码。

### 4.2 fMP4 结构检测器

新增纯 Kotlin、无网络依赖的 ISO BMFF 检测器。检测器只依据合法 Box 边界判断，不进行任意字节串搜索。

可判定为 fMP4 的特征包括：

- `ftyp` 的 major/compatible brand 包含 `dash`、`msdh`、`msix` 或 `dsms`；
- 合法 `moov` 容器内存在 `mvex`；
- 顶层存在合法 `moof`。

解析器同时支持 32 位 Box 长度、64 位扩展长度及“延伸到当前输入末尾”的零长度 Box，并拒绝小于 Box 头、越界、整数溢出、无法前进或嵌套范围非法的数据。

### 4.3 媒体兼容性解析器

新增可注入、可替换测试实现的 suspend 解析器：

- 仅处理 scheme 为 HTTP/HTTPS，且去除查询参数后的路径扩展名为 `.mp4` 的地址；
- 发送 `Range: bytes=0-65535`；
- 接受 `206 Partial Content`，也兼容忽略 Range 而返回 `200 OK` 的服务器；
- 无论响应体声明多大，都只读取最多 64 KiB，然后关闭响应；
- 网络工作在 IO 调度器执行，单次探测使用不超过两秒的总超时；
- 成功判定结果写入最多 128 条的进程内 LRU 缓存；网络失败、取消或结构损坏不缓存，以便后续播放可以重新探测。

缓存键使用最终请求 URL。应用进程退出后缓存自然清空，不新增持久化格式或迁移。

### 4.4 播放协调器与 LibVLC 引擎

`PlaybackCoordinator` 在现有端点选择完成后调用媒体兼容性解析器，再把播放源交给 `PlaybackEngine`。现有串行播放 mutation 在这次有界探测完成后才调用 `prepare`，因此旧媒体的探测结果不能在新媒体已经准备后反向覆盖它。

探测的协程取消会向下传播到 HTTP 调用并关闭响应；服务销毁时不保留后台探测。最长两秒的回退上限保证探测异常不会无限阻塞后续播放操作。

`AndroidVlcPlaybackEngine` 只解释播放源中的解复用策略：

- `AVFORMAT`：在设置媒体并开始解析前添加 `:demux=avformat`；
- `DEFAULT`：不添加新的解复用选项，保持现状。

引擎不自行猜测扩展名或发起网络请求。测试用假引擎可直接记录收到的策略，从而验证路由而不依赖 LibVLC 原生库。

## 5. 数据流

1. 队列或直接播放请求确定当前媒体。
2. 现有服务器会话生成最终请求 URL。
3. 媒体兼容性解析器检查进程内缓存。
4. 缓存未命中且符合 HTTP MP4 条件时，执行最多 64 KiB 的 Range 探测。
5. ISO BMFF 检测器返回是否具有 fMP4 特征。
6. 解析器生成带 `DEFAULT` 或 `AVFORMAT` 策略的播放源。
7. `PlaybackCoordinator` 将播放源交给 `AndroidVlcPlaybackEngine.prepare`。
8. 引擎仅在 `AVFORMAT` 策略下添加 LibVLC 解复用选项，然后沿用现有状态、倍速、恢复位置和自动播放流程。
9. LibVLC 产生正确的原始时间事件；既有会话快照链路继续把它发布给视频 UI。

## 6. 异常与竞态处理

- 非 HTTP/HTTPS、非 MP4 地址不产生额外请求，立即返回 `DEFAULT`。
- HTTP 非成功响应、超时、连接中断、空响应、截断 Box 或非法 Box 均返回 `DEFAULT`，不能阻止播放。
- `CancellationException` 必须继续抛出，不能被通用失败回退吞掉。
- 响应为 `200` 时仍强制执行本地读取上限，不能把完整视频读入内存。
- 探测只读媒体字节，不发送修改请求，也不改变服务器文件。
- 同一 URL 的成功判定在进程内复用，避免队列重播和暂停恢复反复访问文件头。
- 协调器现有串行 mutation 保证同一时刻只有一个媒体准备结果进入引擎；新操作即使等待旧探测结束，也不会被旧结果在之后覆盖。
- 端点故障触发现有备用地址刷新时，新 URL 使用自己的缓存键和判定；不改变现有的一次性端点恢复规则。
- `avformat` 路径若仍发生真实播放错误，沿用现有错误发布和端点恢复，不在默认解复用器与 `avformat` 之间循环重试。
- 日志只记录判定类型和失败类别，不输出完整媒体 URL。

## 7. 测试设计

### 7.1 检测器单元测试

先写失败测试，再实现解析器。覆盖：

- `ftyp` 中的 `dash` major brand 和 compatible brand；
- `msdh`、`msix`、`dsms` 兼容品牌；
- `moov/mvex` 嵌套结构；
- 顶层 `moof`；
- 普通 `isom` 平坦 MP4；
- 32 位长度、64 位扩展长度和零长度 Box；
- 截断头、越界长度、小于头部的长度、整数溢出、非法嵌套和无法前进的 Box。

### 7.2 网络解析器测试

使用本地 MockWebServer 验证：

- 请求携带准确的 `Range: bytes=0-65535`；
- `206` 响应能够识别 fMP4；
- `200` 大响应最多只读取 64 KiB；
- 非成功响应、超时和畸形内容回退到 `DEFAULT`；
- 网络取消能够结束读取并关闭响应；
- 成功判定缓存后第二次不再请求网络；
- 失败结果不缓存，后续请求可以重新探测；
- 非 MP4、非 HTTP/HTTPS 地址不请求网络；
- 含中文、空格、查询参数的已编码 URL 原样传给 HTTP 客户端。

### 7.3 协调器与引擎测试

- fMP4 判定将 `AVFORMAT` 传给引擎。
- 普通 MP4、探测失败和其他格式将 `DEFAULT` 传给引擎。
- `AndroidVlcPlaybackEngine` 只为 `AVFORMAT` 添加 `:demux=avformat`。
- 队列切换、直接 `prepare(url)`、端点恢复及当前项重载均经过同一解析路径。
- 探测期间的媒体操作不会让旧 URL 在新媒体之后进入引擎。
- 现有恢复位置、倍速、自动播放和播放队列测试继续通过。

### 7.4 动态验证

在模拟器或真机上通过 HTTP 服务验证：

- 用户提供的目标样本播放约十秒时显示约 `00:10 / 01:51`，不能跳到 `01:40` 以后；
- 暂停后位置保持不变，恢复后按真实时间继续；
- 向前和向后 seek 后，时间数字、进度条、画面与声音一致；
- 同目录另一份 GPAC fMP4 不再快速跳到末尾；
- 同目录普通平坦 MP4 仍按真实速度计时；
- 网络探测失败时媒体仍能进入原有播放路径。

用户 LAN 地址无法访问或设备不可用时，必须把对应动态项目记录为 `NOT RUN` 或 `BLOCKED`，不能用单元测试或编译结果替代。

## 8. 明确不在本次范围内

- 不修改 Caddy、HTTP Range 服务或服务器映射。
- 不改写、转码、下载替换或重封装媒体文件。
- 不对所有 MP4 或所有媒体全局强制 `avformat`。
- 不升级或降级 LibVLC、Media3、OkHttp 或其他依赖版本。
- 不修改 MediaSession 原始位置快照、UI 轮询周期或进度条计算。
- 不修改播放队列、后台播放、通知控制、恢复位置持久化或视频输出生命周期。
- 不加入基于墙钟的进度修正、跳变限速或静默时间过滤。
- 不进行与本缺陷无关的播放器架构或界面重构。

## 9. 完成标准

- 自动测试证明只有可靠识别出的 fMP4 选择 `avformat`，普通 MP4 保持默认策略。
- 任一探测响应最多读取 64 KiB，失败或超时不会阻止原路径播放。
- 用户目标视频实际播放十秒左右时，UI 位置也在十秒附近，总时长保持约 `01:51`。
- 目标视频暂停、恢复和双向 seek 正常。
- 至少一个普通平坦 MP4 对照样本没有进度、seek 或播放回归。
- 视频、音频、队列、后台播放、恢复进度和通知控制的相关自动测试通过。
- 验证报告明确区分 JVM/编译结果、模拟器结果和真实 LAN 样本结果。
